# Design draft review

Status: independent review of the archived brief, design draft, and README on 2026-10-30. This is a record of open product decisions for a future build, not an approved implementation plan. These decisions do not block completion of the reference archive.

The draft establishes useful boundaries: simulator-independent intent, iRacing as the first target, an empty starting dataset, explicit uncertainty, and separate measured, derived, heuristic, and predicted outputs. No application, live integration, or calibrated vehicle model is established by these documents.

## Decisions that change the build plan

| Open decision | Why the answer changes the plan |
| --- | --- |
| What is the first useful end-to-end outcome: exploring generic interactions, diagnosing a recorded event, comparing controlled setup runs, or supporting an engineer during a live session? | These require different first deliverables. Generic exploration needs explicit assumptions and educational scenarios; recorded diagnosis needs import and event alignment; calibrated comparison needs controlled data collection; live support needs a Windows capture path, freshness handling, and a usable engineer display. The draft's generic-first sequence is a proposal, not a recorded priority. |
| Which first iRacing car, track/layout, and handling event will anchor development, and can the team supply repeatable sessions for them? | Adjustment ranges, telemetry availability, useful model terms, and calibration workload depend on the chosen car and event. Starting fresh means this evidence must be acquired. A kerb disturbance under trail braking can require much finer timing and different measurements than steady-corner balance. |
| What decision must the first model support, and what evidence will make its output useful enough to act on? | Explaining plausible mechanisms, ranking candidate setup changes, estimating response magnitudes, and reporting a grip reserve require progressively stronger identification and validation. The brief's success criteria have no agreed thresholds. The target determines whether replay and heuristics suffice or a calibrated predictive model is necessary. |
| How will the team define and trade speed, stability, repeatability, and recovery for the selected scenario? | A single score cannot be specified from the current brief. Driver objectives and unacceptable behavior affect event labels, experiment design, comparison views, and acceptance criteria. A builder can implement several metrics, but cannot choose the team's preferred tradeoff or tolerance on its behalf. |
| What controlled capture and calibration procedure is feasible in practice? | Available session time, repeat runs, driver participation, and control of fuel, tyres, weather, and track evolution determine whether setup effects can be separated from confounders. This changes experiment design, uncertainty reporting, and the achievable model scope. The documents do not establish a validated collection protocol. |
| Does course progression initially mean summarizing observed laps or predicting a changed setup around a lap? | Observed corner/phase trends can come from replay. Counterfactual responses need a defined maneuver or driver-response assumption and validation. Predicting changed lines or optimal lap time adds a substantially larger capability that is not currently part of the agreed scope. |
| What is the minimum intended deployment and live workflow: who drives, who engineers, on which machines, and with what connectivity? | A local Windows collector with later file import differs materially from a separate engineer watching a shared web application in real time. The answer determines whether live transport, synchronization, storage, team access, and operational support belong in the first milestone. No latency or availability requirement is recorded. |
| What does the requested AI capability need to do first beyond reading evidence? | A procedural skill that helps plan experiments can use archived profiles and reports. AI that invokes calibrated scenarios needs callable deterministic operations, versioned inputs/results, and explicit capability discovery. The draft describes both possibilities without choosing the first deliverable. |

## Scope alignment and points to preserve

- **No direct contradiction was found** among the reviewed documents. They consistently supersede the earlier LMU-first assumption, identify iRacing as the current priority, and avoid assuming existing telemetry or calibration assets.
- **SimHub plus a web application is a user suggestion.** Calling SimHub the preferred initial collection host is reasonable as a proposal, but does not establish an approved dependency or prove channel coverage. A future builder must audit the chosen iRacing car's actual channels before committing the engineering model to that transport.
- **Simulator independence is a product boundary, not evidence of portability.** The first implementation can target iRacing while preserving source identity and capabilities. It must not silently reuse iRacing-specific channel meanings, adjustment rules, or calibrated coefficients for another simulator.
- **AI-readable car limitations are a core requirement.** A future profile needs to expose legal adjustment limits and dependencies, unavailable channels, unsupported calculations, calibration domain, and revision identity. Import/export alone does not satisfy this requirement if the AI cannot tell which conclusions the profile supports.
- **Generic scenarios remain proposed and uncalibrated.** They may help before recordings exist, but cannot establish the real car's grip envelope or demonstrate a setup improvement. Similarly, the reference overlay and LMU setup process do not validate an iRacing vehicle model.

Framework selection, file layout, charting libraries, transport implementation details, and ordinary internal API design can be chosen by the builder once the above outcome and operating constraints are known. They do not need to delay the archive or become additional user decisions now.
